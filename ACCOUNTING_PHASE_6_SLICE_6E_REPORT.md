# Accounting Phase 6, Slice 6e — Nepal Tax Depreciation (Pooled Declining-Balance)

## What was built

Per `ACCOUNTING_PHASE_6_PLAN.md` Part 3's 6e, this slice adds a second, independent depreciation computation for fixed assets: Nepal's Income Tax Act 2058, Schedule 2 method (pooled declining-balance for four asset pools, straight-line for intangibles), alongside — and never touching — Slice 5d's existing straight-line **book** depreciation.

- Each fixed asset can now be classified into one of five Nepal tax pools: **A** (buildings/structures, 5%), **B** (computers/furniture/office equipment, 25%), **C** (automobiles/buses/minibuses, 20%), **D** (construction equipment and catch-all, 15%), or **E** (intangibles — not pooled, straight-line). Classification is manual and nullable — this app never guesses an asset's pool from its free-text `category`, so an asset has no tax pool until an owner explicitly sets one, done inline from the Fixed Assets tab.
- A new **Tax Depreciation** report (alongside the existing VAT Return report) computes, per Nepali income year (Shrawan 1 – Ashadh end): for pools A–D, one aggregate balance per pool with additions and disposal proceeds netted in before the flat rate applies; for pool E, per-asset straight-line over the asset's own useful life.
- The report is entirely **read-only** — it posts nothing to the ledger and never reads or writes any Slice 5d book-depreciation field. It is a reference computation for the owner's or accountant's own use, the same framing as Slice 6c's VAT Return: not a filable IRD schedule, not an accounting entry.
- A mid-year acquisition uses the Act's own "thirds" coefficient rather than day-count proration: an asset added in the first six months of the income year (Shrawan–Poush) counts in full that year; added in the next three months (Magh–Chaitra), two-thirds counts this year and the remaining third carries forward as an addition to the pool next year; added in the last three months (Baisakh–Ashadh), only a third counts this year and two-thirds carries forward.
- A disposal subtracts the asset's actual **sale proceeds** (not cost, not book value) from its pool in the income year of disposal, resolved from the disposal's own accounting-effective date, not the timestamp the disposal happened to be entered into the app. If proceeds exceed the pool's pre-depreciation value, the excess is flagged as a **balancing charge** (taxable income, not depreciation) and the pool resets to zero.
- If a pool's pre-depreciation value is positive but under Rs. 2,000, the report flags it as fully written off that year rather than continuing at the flat rate (the Schedule 2 de-minimis rule).

## The decision this slice needed, and how it was resolved

Live web research into the actual Schedule 2 mechanics (cross-checked across several independent sources, since neither the plan document nor training data could be trusted as authoritative on current Nepali tax law) turned up a split in source confidence: the four pool rates and the "thirds" mid-year coefficient were corroborated consistently across four-plus independent sources (high confidence). The disposal balancing-charge mechanic and the Rs. 2,000 de-minimis write-off were corroborated by fewer, lower-tier sources, with no official gazette text reachable (medium confidence).

This was put to `AskUserQuestion` as a genuine scope/risk fork: implement the full mechanic including the medium-confidence disposal and de-minimis rules, clearly caveated in the UI and code comments; or scope down to only the high-confidence pool-rate/coefficient core, leaving disposals unhandled (safer, but silently wrong or incomplete the first time a pooled asset is actually disposed). The user selected **"Full mechanic, clearly caveated (Recommended)"**. Accordingly, the report carries a prominent verification-status banner naming exactly which figures rest on which confidence tier, both in the UI and in `tax-depreciation.ts`'s own top-of-file comment — this is deliberately not soft-pedaled, since a wrong balancing-charge or de-minimis figure taken at face value could misstate taxable income.

## A sub-decision made without asking, and why

The Act's thirds coefficient is specified for the four pooled categories; research did not turn up a separately-sourced rule for intangibles' first-year charge under the straight-line method. Two options existed: prorate by day count (matching Slice 5d's own book-depreciation convention), or reuse the same thirds coefficient as the pools. Day-count proration was rejected — the research had specifically flagged day-count as the *less* credible convention for this jurisdiction, contradicted by sources quoting the Act's actual text for the pooled categories. Reusing the thirds coefficient for intangibles keeps the module internally consistent, but this is documented explicitly in code as the module's own choice, not an independently-sourced fact, since it was never itself directly verified for the intangible case.

One consequence worth noting: because there's no remainder carry-forward for non-pooled assets (unlike the pools, where an unabsorbed third rolls into next year's addition), an intangible asset acquired mid-year simply finishes depreciating later than its nominal useful life — e.g. an 18-month-life asset acquired at the start of the last third of an income year takes three income years, not 1.5, to fully depreciate. This is covered by a dedicated test.

## Deliberately out of scope

- **Filing/export to an IRD-specific schedule format.** This is a reference computation for internal use, not a filable government form — consistent with how Slice 6c's VAT Return report is framed.
- **Auto-classifying an asset's tax pool from its category.** This app has no authoritative mapping from free-text asset categories to Schedule 2 pools; guessing wrong here has real tax consequences, so classification stays a deliberate, manual, per-asset action.
- **A persisted running-balance/pool table or a scheduled recompute job.** Matches this codebase's established "deliberately human-triggered, never a background cron" convention (the same reasoning already applied to Slice 5d's own `run-depreciation` route and to Slice 6b's decision against auto-applying future-dated tax rate changes). The report is computed fresh from `fixedAssets` and `accountingVouchers` on every request.
- **Resolving the medium-confidence mechanics (disposal balancing charge, Rs. 2,000 de-minimis) against an official gazette source.** Implemented per the user's sign-off on "full mechanic, clearly caveated," but the caveat itself is a permanent, intentional feature of this report, not a placeholder to be quietly removed — an owner or accountant relying on a balancing-charge or de-minimis figure should independently confirm it against current IRD guidance before filing.
